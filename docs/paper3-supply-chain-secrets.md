# Supply Chain Security and Secrets Management — Abliterated Model Runtime

**Scope:** target-state design, same caveat as Papers 1 and 2.

## 1. Image Scanning and Signing

The container built in Paper 1 carries two distinct risks: known CVEs in the base layer, and tampering between build and deploy. Scanning addresses the first, signing addresses the second. Neither substitutes for the other.

**Scanning**
- Scan every image in CI before push, and every image already in the registry on a recurring schedule (Trivy or Grype, either works, pick one and standardize). Fail the CI build on CRITICAL findings with a known fix available; HIGH findings get a ticket, not an automatic block, or velocity dies.
- Scan the GGUF model artifact's provenance too, not just the OS layer. Where did the quantized model file come from, and does its hash match what the build stage expects? This matters more than usual here since the whole point of the workload is a modified model; a silently swapped model file is a supply-chain attack with no CVE signature to catch it.

**Signing**
- Sign every image with Sigstore cosign, keyless signing tied to the CI identity (OIDC), rather than a long-lived signing key that becomes one more secret to protect.
- Enforce signature verification at admission (Kyverno or the equivalent policy engine) so an unsigned image cannot be scheduled into the namespace, full stop.
- Attach an SBOM (CycloneDX or SPDX, generated by the same scanner) as a signed attestation on the image. This gives you a queryable answer to "are we exposed to CVE-X" without re-scanning every running image manually.

## 2. Secrets Management

The current setup has exactly one secret that matters: the bearer token, held in `heretic_proxy.env`, kept out of git by `.gitignore`. That's adequate for a single VM. It does not scale to a cluster with multiple workloads, rotation requirements, or more than one person needing access.

**Vault (HashiCorp Vault or equivalent)**
- Move the bearer token, and any future API keys or model registry credentials, into Vault. Nothing sensitive lives in a `.env` file or a Kubernetes Secret as the source of truth, both are just delivery mechanisms for a value Vault actually owns.
- Use dynamic secrets where the backing system supports them (short-lived cloud credentials, database creds). The bearer token itself is application-level and will likely stay a static secret with scheduled rotation, since the Cloudflare Worker and Caddy both need a stable value to check against; rotate on a fixed cadence (recommend 30 to 90 days) rather than never, which is the current state.
- Vault Agent or the Vault CSI driver injects secrets into the pod at runtime as a projected volume, not as environment variables. Env vars leak into process listings, crash dumps, and child processes; a mounted file with tight permissions doesn't.

**Cloud-Native Secrets**
- If Vault is more infrastructure than the current stage warrants, the minimum acceptable bar is AWS Secrets Manager (matching the existing AWS deployment) with automatic rotation configured, referenced into Kubernetes via the External Secrets Operator, not copy-pasted into a raw Kubernetes Secret manifest.
- Either way, raw Kubernetes Secrets (base64, not encrypted at rest by default) are a delivery layer only. Enable encryption at rest for the etcd Secrets resource (KMS provider) regardless of which backend feeds it.
- The Cloudflare Worker's copy of the token (currently server-side in the Worker, correctly never reaching the browser) should pull from the same source of truth via Worker Secrets bound at deploy time, not a manually copied value that drifts from what Vault or Secrets Manager has.

## 3. Implementation Path

1. Stand up scanning in CI first, it's the lowest-effort, highest-immediate-value step and requires no cluster.
2. Add cosign signing and SBOM generation to the same CI pipeline once scanning is stable.
3. Stand up Vault (or Secrets Manager, pick one, don't run both) and migrate the bearer token as the first secret, proving the rotation workflow end to end.
4. Add signature verification and Vault injection as admission-time requirements only after both are proven in a non-production namespace, then enforce.
5. Update `HANDOFF.md` and `RUNBOOK.md` to reflect the new secret source of truth, so the next person doesn't go looking for a `.env` file that no longer exists.

## 4. Open Questions

- Vault self-hosted (another thing to secure and patch) or Vault-as-a-service (HCP Vault) or straight to AWS Secrets Manager? This is a cost and ops-burden tradeoff, not a security one; all three are acceptable, the choice is yours.
- Who is the second person authorized to rotate secrets, for continuity if you're unavailable? Not currently defined anywhere in the repo.
